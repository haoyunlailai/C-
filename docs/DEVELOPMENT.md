## 协作模式

人和 AI 的分工不是「人提需求、AI 写完交付」，而是一个短周期闭环：

```
需求 → AI 生成实现 → 人运行验证 → 复现问题 → AI 定位/修复 → 回归验证
```

- **人负责**：需求边界（支持哪些应用、是否允许自定义路径）、验收标准、真实环境测试、不可逆操作的判断；
- **AI 负责**：跨文件实现、算法编码、编写复现脚本、分析异常栈、重构与文档；
- **关键习惯**：先让 AI 写出「能稳定复现 bug 的脚本」，再让它修。修复后必须重跑同一脚本。

## 关键决策

| 决策点 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| GUI 框架 | Tkinter + ttk | 标准库自带，exe 体积小，无运行时依赖 | 控件定制能力有限，需手工绘制可视化 |
| 删除策略 | 默认移入回收站；应用缓存直接删除 | 用户文件可恢复；缓存可再生，且 send2trash 在 8.3 短路径上失败 | 缓存删除不可恢复 |
| 重复文件检测 | 先按大小分组，再对同大小文件算 MD5 | 避免对全盘文件哈希，I/O 大幅减少 | 极端情况下仍需哈希大文件 |
| 未使用判定 | 安装目录内文件的最新 mtime 超过 180 天 | 完全离线、不采集使用行为数据 | 长期只读运行的软件可能误判 |
| 树状图算法 | Squarified Treemap | 长宽比接近 1，方块易读、易点击 | 实现复杂度高于简单切分 |
| 下钻导航 | 缓存父节点对象（`_node_stack`） | 返回操作 O(1)，不再重扫磁盘 | 内存随下钻层级增长（可接受） |
| 安装路径 | `InstallLocation` → `DisplayIcon` → `UninstallString` 依次尝试 | 注册表字段大量为空，逐级兜底提高覆盖率 | 推断结果可能与真实目录有偏差 |
| 数据存储 | 无云端、无数据库、无日志上传 | 隐私优先，符合清理工具的信任预期 | 无历史趋势分析 |

## 调试案例

### 1. 第二次删除重复文件无反应

- **症状**：第一次删除成功，第二次勾选后点击删除毫无反应。
- **复现**：脚本创建两组重复文件，连续执行「扫描 → 删除」两轮，捕获到 `TclError: Item I006 not found`。
- **根因**：`Treeview.delete()` 删除父节点时会级联删除子节点；原代码先删父组、再 `get_children(父组)`，第二轮父组已不存在。
- **修复**：先取子节点快照，再删除父节点。
- **验证**：同一脚本连续三轮扫描删除通过。

### 2. 缓存清理后数值不变

- **症状**：提示清理完成，但界面上的缓存大小没有变化。
- **复现**：在删除循环中记录异常，发现 `send2trash` 抛出 `WinError 161（指定的路径无效）`，路径包含 8.3 短名（如 `QQBROW~1`）。
- **根因**：异常被 `except` 吞掉并计为失败，界面仍显示成功；且该路径模式下 send2trash 无法工作。
- **修复**：缓存文件改用 `os.remove`；失败数量如实展示；清理完成后自动复扫刷新数值。
- **验证**：清理前后对目录总大小做对比。

### 3. 应用缓存扫描报参数错误

- **症状**：扫描中途报 `TypeError: progress_cb() missing 1 required positional argument: 'ratio'`。
- **根因**：扫描器以单参数调用进度回调，而 UI 层回调签名为 `(text, ratio)`。
- **修复**：统一回调契约，所有调用点补齐比例参数。
- **教训**：跨模块回调必须显式约定签名，不能靠调用方自觉。

### 4. Treemap 部分方块消失

- **症状**：15 个同级条目只渲染出 5 个，矩形面积总和 7000，而容器面积为 10000。
- **复现**：用 4 个已知大小的节点（50 / 30 / 15 / 5）做面积守恒断言，两个条目被跳过。
- **根因**：布局循环中 `for _, a in row` 遍历的同时 `row.pop(0)`，迭代索引前移导致元素被跳过；此外剩余空间小于阈值时循环提前退出，尾部条目被丢弃。
- **修复**：改为 `while row: row.pop(0)` 显式消费；空间耗尽时兜底放置剩余项。
- **验证**：4 个节点面积精确为 5000 / 3000 / 1500 / 500，总和等于 10000。

### 5. 返回上一层缓慢

- **症状**：在树状图中返回上一级需要数秒，明显重新扫描了磁盘。
- **根因**：返回操作调用 `scan_drilldown` 重新遍历目录。
- **修复**：维护节点栈保存父节点对象；下钻已访问过的节点也直接命中缓存。
- **验证**：返回耗时从秒级降至约 2 ms。

### 6. 软件安装位置大面积缺失

- **症状**：150 个已安装软件中只有 58 个能显示安装路径。
- **根因**：注册表 `InstallLocation` 在大量安装包中为空。
- **修复**：依次尝试从 `DisplayIcon`、`UninstallString` 提取目录，跳过 MSI 产品码与 `msiexec` 命令。
- **验证**：覆盖率提升至 86 / 150。

## 如何验证 AI 生成的代码

1. **数据层脚本直测**：不启动 GUI，直接调用扫描器，对大小、面积、数量做断言；
2. **GUI 程序化驱动**：实例化 Tk 窗口并直接调用页面方法，验证渲染数量与控件状态；
3. **破坏性操作先构造样本**：在临时目录生成重复文件、假缓存目录，再跑完整流程；
4. **边界覆盖**：无权限目录、空目录、零字节文件、8.3 短路径、超长路径；
5. **打包后真机验证**：运行最终 exe，逐 Tab 走一遍主流程。

## 复盘

**AI 擅长的**：快速搭建骨架与跨文件重构；把报错栈翻译成假设；生成可重复的复现脚本；保持一致 UI 约定。

**人必须盯的**：验收标准（扫描要扫哪些路径）；被 `except` 吞掉的异常（案例 2 的失败其实一直存在）；不可逆操作的安全边界；真实数据下的表现（案例 6 的覆盖率只有跑真实注册表才会暴露）。

**结论**：Vibe Coding 提高的是「实现速度」，不降低「验证责任」。对删除类工具，验证成本必须计入开发预算——这也是本项目每个模块都配自测脚本的原因。
